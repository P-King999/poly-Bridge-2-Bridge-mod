# Poly Bridge 预算修改器 · 开发过程复盘

按时间线记录从"连上手机"到"HUD 真的变成 $999,999"的全过程，每个坑按 **现象 → 原因 → 解决** 写。

## 0. 起点：ADB 连接与 root

设备是 Redmi K40（型号 `M2012K10C`，代号 `ares`），Android 13 / MIUI，序列号 `hqvkxkeqfqo7p7ce`。
第一步确认 root：

```bash
adb shell su -c id
# uid=0(root) gid=0(root) groups=0(root) context=u:r:magisk:s0
```

拿到 `u:r:magisk:s0` 就意味着后面的 `/proc/<pid>/mem` 访问有了合法身份。
Magisk 28.1（28100），SELinux 保持 `Enforcing`，不需要关。

## 1. 第一个坑：`input tap` 用的是横屏坐标

**现象.** `adb shell input tap X Y` 点游戏按钮毫无反应，但同一套坐标有时又能点中 UI。
**原因.** 屏幕物理 1080×2400、density 440，看着是竖屏；但游戏强制横屏，
`dumpsys` 里 `mDisplayRotation=ROTATION_90`，此时 `input tap` 接受的是**旋转后的逻辑坐标，即 2400×1080**。
按竖屏算出来的坐标只要 `y > 1080` 就**静默失败**——不报错，不生效。
**解决.** 固化映射关系：**`input tap` 的坐标 == 横屏截图的像素坐标**，
直接从 2400×1080 截图里读像素，不做任何换算。

顺带修掉一个截图小坑：`adb exec-out screencap -p` 在某些机型上输出损坏的 PNG，改成
`adb shell screencap -p /sdcard/sN.png` 再 `adb pull`。另外游戏冷启动要先等约 **25 秒**闪屏。

## 2. 反汇编：自写 ildump.exe

目标是 Mono 后端，IL 都在 `Assembly-CSharp.dll`（2,477,056 字节）里，所以先读代码而不是盲扫内存。
但机器**没有网络**，装不了 ILSpy / Mono.Cecil / dnlib。于是用 .NET 自带的
`System.Reflection.Metadata` 写了个小工具 `ildump.exe`，三种模式：`list` 列类型、
`type <类型名>` 列方法、`il <Type::Method 正则>` 反汇编匹配的方法。

这里踩过一次用法错误：`il` 模式匹配的是 `"Type::Method"` 形式的**正则**，不是类型名。
参数改对后做全量转储 `ildump.exe Assembly-CSharp.dll il "." > all.il`，约 **456,413 行、耗时约 6 秒**，
并直接拿到了方案最核心的几张事实表：`SetBudget` 只有 2 个调用点、
`RemoveGameObject IL_0203` 是最省事的刷新触发点、`LevelParametersScript.Setup IL_0124` 会重新灌预算。

## 3. 顺路逆向存档格式（以及一条死路）

在认定"必须改内存"之前，先试过"改存档"这条更温和的路。

**成果.** 存档格式被完整逆出来，没有任何加密：
`JSON → UTF8 字节 → Utils.CLZF2.Compress → Convert.ToBase64String`，关键常量是
`HLOG=14`、`HSIZE=16384`、`MAX_LIT=32`、`MAX_OFF=8192`、`MAX_REF=264`。
照这个规格实现的 CLZF2 + Base64 命令行工具，**解出来和压回去都能对上**。
路径规律：`persistentDataPath` 是 `/sdcard/Android/data/com.drycactus.hq.polybridge/files/`，
下面是 `savefiles/{levelName}/{file}`；常量 `SAVEFILESROOT="savefiles/"`、
`AUTOSAVENAME="AUTOSAVE"`、`BUDGETAUTOSAVENAME="BUDGET"`。

**死路.** 看到一个叫 `BUDGET` 的存档文件，第一反应是"预算就在这"。
解出来发现**它是一份桥梁设计（结构数据），不是预算数值**——预算写在关卡参数里，从来不落盘。
另一个失败尝试：手动把 `<string name="SettingsLastPlayedLevel">Easy_001</string>` 写进 playerprefs，
想让它启动时自动进那一关——**无效**，游戏没理这个键。

**结论.** 存档路线关闭，回到内存路线。但这段没白做：它确认了"预算是关卡常量、不随存档走"，这正是本工具"只在内存里改"的底气。

## 4. 原生扫描器 `pbmem.c` 的五次迭代

跨进程读写需要一个设备端可执行文件。`pbmem.c` 支持 `scan` / `scanctx` / `dump` / `write` /
`patch` / `patchall` / `pair` / `regions`，它前后被打回五次，每次都是一个真实的 bug。

### 4.1 静态链接导致 Bionic 拒绝执行

**现象.** NDK 编译出的二进制一执行就失败：

```text
executable's TLS segment is underaligned: alignment is 8 (skew 0),
needs to be at least 32 for ARM Bionic
```

**原因.** 链接时加了 `-static`，NDK 的静态 libc 会产生对齐只有 8 的 TLS 段，而 Bionic 要求至少 32。
**解决.** 去掉 `-static`，改成 `-O2 -fPIE -pie` 链接；产物变成 `Type: DYN`、
带 `INTERP /system/bin/linker`、**没有 PT_TLS**，设备上正常执行。

### 4.2 32 位 `off_t` 让高位地址静默读不到

**现象.** 扫描只命中十几个地址，且全在框架区域，游戏数据一个都没有。
**原因.** 32 位 ARM 的 `off_t` 默认 32 位有符号，`pread(memfd, buf, len, (off_t)addr)`
在地址超过 2 GB 时**静默失败或截断**。而 Unity 托管堆正好在 2 GB 以上。
**解决.** 加上 `#define _FILE_OFFSET_BITS 64` 和 `#define _LARGEFILE64_SOURCE`，
命中数 **16 → 96**，是整个项目里"一个宏改变一切"的一次。

### 4.3 分块失败就 `break` 导致整段漏扫

**现象.** 修完 `off_t` 后命中数上来了，但同一数值在不同时刻扫出的数量波动很大。
**原因.** `/proc/<pid>/mem` 里存在读不出来的空洞（未映射页），这是常态；
原代码在单个 1 MB 分块 `pread` 失败时直接 `break`，**该区域剩下的部分全部放弃扫描**。
**解决.** 失败时改为 `if (got <= 0) { chunks_fail++; addr += 4096; continue; }`，跳过一页继续并单独计数。

### 4.4 未对齐的 4 字节窗口会破坏相邻字段

**现象.** 出现一批"命中、位置却很奇怪"的地址，例如 `0x6feced9a`、`0x715c680b`、
`0xbe20bca2`、`0xf376268a`，全都不是 4 的倍数。
**原因.** 扫描用 `o++` 逐字节滑动 4 字节窗口，**横跨两个 int32 的窗口**也会被匹配并写下去，
同时破坏两个真实字段（图解见《技术原理》第 7 节）。
**解决.** 在 `scan_value` / `patchall` / `pair` / `patch` 四处都加上
`if (((addr + (uint64_t)o) & 3) != 0) continue;`。
**效果.** 同一数值的命中数从约 **96 降到 46**，少掉的正是假命中——这个数字后来和端到端实测对上了。

### 4.5 整块回写会回滚游戏的并发修改

**现象.** 早期 `patchall` 偶发把游戏搞成异常状态。
**原因.** 它把整个 1 MB 缓冲 `pwrite(memfd, buf, got, addr)` 写回去，
**游戏在扫描期间对该分块做的任何并发修改都会被一起回滚**，还可能把数值写成半个旧值半个新值。
**解决.** 改成**先扫描收集地址 → 逐个重新读确认没变 → 只写这 4 个字节**
（`read_value` 失败或值已变就跳过并计入 `raced`），让 `write_value` 循环直到 4 字节写完，并跳过文件映射区域。

### 4.6 `strtoul(NULL)` 崩溃与参数守卫

**现象.** `pb.sh patchall 7000`（少给一个参数）直接段错误。
**原因.** 只检查了 `argc < 4`，而 `argv[4]` 在 `argc == 4` 时是 `NULL`，`strtoul(NULL, ...)` 当然崩。
**解决.** 给每个会解引用 `argv[4]` 的模式加 `if (argc < 5) { usage(argv[0]); return 1; }`；
顶层守卫从 `argc < 4` 放宽到 `argc < 3`（`regions` 本来只需两个参数，之前必须塞个假参数）。
设备端脚本还要注意：mksh 没有 `grep -P`；对 `/proc/pid/mem` 用 `od -j` 会报 I/O 错误（要用 `xxd -s`）；
mksh 的算术是 32 位的。所以复杂逻辑一律**写成 `.sh` 推上去再执行**。

## 5. 离线打包链

这台机器**完全没有网络**：装不了 Gradle，也拿不到任何依赖。解决方式是用 Android SDK 自带命令行工具手搓流水线：
`aapt2 link` → `javac --release 11` → `d8` → `ZipArchive`（补 `assets/pbmem`）→
`zipalign -f 4` → `apksigner sign`，依次产出 base.apk、.class、classes.dex、带资源的包、
aligned.apk、budget-mod.apk。工具链：build-tools **35.0.0 / 36.0.0**、
platforms **android-35 / android-36**、NDK **27.1.12297006**、cmake 3.22.1、javac 23.0.1。

**坑一：`keytool` 不在 PATH。** `apksigner.bat : Failed to load signer "signer #1"`——生成 keystore
需要 `keytool`，它只躺在 `C:\Program Files\Java\jdk-23\bin\keytool.exe`，PATH 里没有。解决：显式写全路径调用。

**坑二：`aapt add` 写进去的是反斜杠。** 条目变成 `assets\pbmem`，而 `AssetManager` 解析不了
反斜杠路径，`getAssets().open("pbmem")` 必然失败。解决：改用 .NET `ZipArchive` 手动加条目、
路径显式写正斜杠 `assets/pbmem`，并在构建脚本里加断言——**zip 里出现反斜杠条目就直接失败**。

**坑三：构建脚本会"假成功"。** 最初的 `build.ps1` 用 `$ErrorActionPreference='Continue'`
且**从不检查 `$LASTEXITCODE`**。后果是某一步失败而旧的 `aligned.apk` 还在时，
脚本会把一个**过期 APK** 签出来并报告成功。解决：重写脚本，每步用 `Invoke-Tool` 包装并检查退出码，
**开跑前先删掉 base.apk / aligned.apk / budget-mod.apk**，
结束前跑 `zipalign -c -v 4` 与 `apksigner verify --print-certs` 自检，
并用 `keytool -list` 校验 keystore 可读。

**坑三的续集：PowerShell 7.4 的 stderr 陷阱。** 改完之后脚本反而在 `javac` 那步中止，
报 `NativeCommandError`。原因是 javac 在 stderr 上打了一句无害的"使用了已过时的 API"，
而 PowerShell 7.4 在 `$ErrorActionPreference='Stop'` 下**把原生程序的 stderr 当成终止性错误**；
设 `$PSNativeCommandUseErrorActionPreference = $false` 在这个环境里**无效**。
可行写法：把外部命令输出用 `2>&1` 捕获进变量，再自己判断 `$LASTEXITCODE`。

## 6. 为什么必须做成独立 App

游戏没有 `SYSTEM_ALERT_WINDOW` 权限（`com.lerist.autocmd` 有、`li.songe.gkd` 是 `ignore`），
所以面板只能是独立 APK（`com.pbmod.budget`）。独立之后立刻撞上 Android 12+ 的限制。

**现象.** 从 shell 启动前台服务，两种方式都失败：非 root 时 `am start-foreground-service` 报
`Requires permission not exported from uid 10296`；用 `su -c` 则 logcat 报
`Background start not allowed: ... startFg?=true`。
**原因.** Android 12 起**前台服务不允许从后台启动**，root 也不行——
系统看的是"发起者是不是前台"，而不是"发起者是不是 root"。
**解决.** 面板必须由 App **自己的前台 Activity** 启动。`MainActivity` 做了
「打开悬浮面板」/「关闭悬浮面板」两个按钮，另留自动化钩子
`adb shell am start -n com.pbmod.budget/.MainActivity --ez auto true`——这个 `auto` 分支后来
补上了悬浮窗权限检查，之前它会绕过 `canDrawOverlays()` 直接开出一个看不见的僵尸前台服务。

## 7. 悬浮窗的四个坑

**7.1 `adb install -r` 会重置悬浮窗权限。**
现象：面板"打开了"但屏幕上什么都没有，`dumpsys` 里窗口存在却是
`mAppOpVisibility=false ... isOnScreen=false`。
原因：每次覆盖安装系统都会**重置该应用的 app-op**，包括 `SYSTEM_ALERT_WINDOW`。解决：

```bash
adb shell appops set com.pbmod.budget SYSTEM_ALERT_WINDOW allow
```

**7.2 可聚焦窗口会暂停 Unity 并吞掉外部点击。**
现象：面板一出现游戏就卡住，点面板以外也没反应。原因：窗口默认可聚焦，会让 Unity
**失去焦点而暂停**，且模态地吃掉面板以外的触摸。解决：加
`FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL`，面板从此不暂停游戏。

**7.3 Dialog 主题下 `Button` 渲染不出来。**
现象：面板显示成"标题 + 一大片空白 + 按钮挤在最下面"，键盘和操作按钮完全看不见。
原因：清单里用了 `@android:style/Theme.DeviceDefault.Dialog.NoActionBar`，这个主题应用到 Service 上时
普通 `Button` 拿不到可见背景（全透明），于是"有控件、有响应、但看不见"。
解决：所有控件换成 `TextView`，**显式**设置文字颜色和 `GradientDrawable` 背景，每行给固定 dp 高度；
之后发现面板比 1080 px 屏幕还高，又把宽度 232→216 dp、按键 36→32、`lp.y` 从 140 移到 14 dp。

**7.4 MIUI 输入法送不进不可聚焦窗口。**
现象：面板本来有两个 `EditText`；因为窗口是 `FLAG_NOT_FOCUSABLE`，点它弹不出输入法，
偶尔弹出来**输进去的字也进不到框里**。原因：不可聚焦窗口拿不到输入焦点，MIUI 输入法无法投递文本。
解决：**彻底放弃 `EditText` 和输入法**，改成纯触摸数字键盘 `7 8 9 / 4 5 6 / 1 2 3 / 清空 0 ⌫`，
不弹输入法、不需要焦点。数字存在 `valOld` / `valNew` 里，`parse()` 拒绝空值、非数字、
以及 `<= 0` 或 `> 2000000000` 的值。
**后续小修**：键盘原先把输入限制在 9 位，而 `parse()` 允许到 20 亿（10 位），
于是输入 `1000000000` 时第 10 次按键被**静默丢掉**，剩下 `100000000`——一个"合法但错误"的值会被应用。

## 8. `su` 卡死与"假成功"

**8.1 无响应的 `su` 会永久卡死线程池。**
现象：某次 Magisk 授权弹窗没人点，面板从此永远停在"准备中…"。
原因：面板用单线程 `ExecutorService` 跑 `su`，而 `Process.waitFor()` **没有超时**，`su` 一挂就永久占用唯一的线程。
解决：三层一起改——用守护线程持续**排空 stdout**（否则管道写满也会死锁，主线程无法安全超时）；
`waitFor(TIMEOUT_MS /* 120000 */, MILLISECONDS)`；超时后 `destroyForcibly()` 并追加标记 `PB_TIMEOUT`。
同时把 `ready()` 从 `endsWith("PBREADY")` 改成 `contains("PBREADY") && !contains(TIMEOUT_MARK)`，
因为 `redirectErrorStream(true)` 把 stderr 并进了 stdout。

**8.2 "只要输出里有 patchall 就报成功"。**
现象：面板显示"已完成"，游戏里什么都没变。
原因：成功判断写成"输出包含 `patchall` 字样"，而 `replaced 0`、甚至 `pidof` 返回两个 PID
导致程序打印 `usage()`（usage 文本里就有 `patchall`）都会命中。
解决：用正则 `replaced\s+(\d+)\s*,\s*write-failures\s+(\d+)` 解析真实计数。
`replaced == 0` → "没有找到 X (0 处)"；`write-failures > 0` → "替换 N 处, M 处写入失败"；
否则 → "已完成: N 处 -> X。回游戏删掉一块材料即可刷新"。

**8.3 设备上的辅助二进制是旧的。**
现象：明明重新编译了 `pbmem`，手机上的行为却没变。
原因：部署脚本是 `if [ ! -x /data/local/tmp/pbmem ]; then cp ...; fi`——**只在文件不存在时才拷**，
而 `/data/local/tmp` 在卸载重装后依然存在，所以永远拷第一次那份。
解决：改成用 `cmp -s` 比对内容，并走"临时文件 + 原子改名"：`cp` 到 `pbmem.tmp` → `chmod 755` →
`mv -f` 覆盖，失败再退回"先 `rm` 再 `cp`"（先 `rm` 是为了避开 `ETXTBSY`）。

## 9. 端到端成功的那一刻

游戏进到关卡 1-3，HUD 上写着：绿色 `$ 9,090` 是**已经花掉的钱**，
它下面那行 `预算: $10,000` 才是预算。面板上点「当前:」输入 `10000`，
点「改成:」输入 `999999`，点「应用」，状态行显示
`已完成: 46 处 -> 999999。回游戏删掉一块材料即可刷新`。

**关键的最后一步.** 此时 HUD **仍然显示 $10,000**（原因见《技术原理》第 4 节）。
回游戏点中一段路面删掉，触发 `RemoveGameObject IL_0203 → UpdateBudgetUI`，HUD 立刻变成：

```text
$ 2,306           ← 删掉一段路后重新计算的已花费
预算: $999,999     ← 预算被成功改掉了
```

**收尾验证.** 又做了一次不依赖游戏的独立往返测试，起一个一次性 `sleep` 进程当靶子：写入
`0x7f5dfff000 = 424242` 后读回一致，`scan` 命中 1 处，`patchall` 返回 `replaced 1, write-failures 0`。
**最终产物.** APK 29,133 字节，SHA-256 `5317E661…`；把手机上已安装的 APK 拉回来比对，
**哈希完全一致**；设备端 `/data/local/tmp/pbmem` 也确认是刷新后的新版（15,096 字节）。

## 10. 复盘

最值得记住的一条是：**先读代码，再碰内存**——反汇编省掉了大量盲扫。
其次是**静默失败最贵**：`off_t` 截断、未对齐窗口、`y>1080` 的 tap、9 位输入上限，全都不报错；
而"看起来成功"必须单独验证——假成功提示、过期 APK、旧版辅助二进制是同一个病。
工程上则是**脚本必须假设工具会失败**：检查每个退出码、先删旧产物、最后自检签名与对齐。

还有一条来自用户视角的体会：**技术上"改成功"和用户看到"改成功"是两件事。**
内存确实改了，但 HUD 不刷新，用户就会认为工具坏了，
所以交付时必须把"应用之后要回游戏放/删一块材料"写在最显眼的位置。
